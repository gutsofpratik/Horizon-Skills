# 判据细则 · 五问的证据标准

SKILL.md 是流程，这里是判案的细节。逐 skill 过堂时按本文取证。

## 一、三分法怎么定类型

对每个 skill 问三个问题：

1. **把它给一个陌生公司的同款模型用，还成立吗？** 成立 → 不含私有事实，偏能力型 / 环境型；不成立 → 含知识型成分。
2. **它的正文在「教方法」还是「报事实」？** 教方法（怎么想、怎么写、分几步）→ 能力型；报事实（哪台主机、哪个账号、哪条内部规矩）→ 知识型。
3. **删掉它之后，模型是「变笨」还是「变瞎」？** 变笨（做得没那么好）→ 能力型，可盲测验证；变瞎（根本不知道该连哪、找谁）→ 知识型，红线保护。

**混合型**最常见：一层通用说教（能力型，可删）包着几行私有事实（知识型，必留）。判决用 🔧 修剪，不用 ✂️ 移除。

## 二、五问的证据标准与典型案例

### 问 1 · 模型已内化？（能力型专属）

**证据标准**：盲测（见第三节）裸做质量不逊于 skill 承诺的产出。没跑盲测就下 ✂️，属于嘴判，不许。

容易中招的典型（2023–2024 年的刚需，如今多为模型本能）：

- 分步思考 / 自我反思脚手架（think step by step、先计划再执行模板）
- 通用代码评审清单、通用调试流程、通用重构指南
- commit message / PR 描述写法教程
- 总结、翻译、改写的提示词模板
- 提示词格式技巧（XML 标签、few-shot 排版指南）

**容易误杀的反例**：

- 看似「通用清单」，实则编码了团队取舍（「我们宁可重复也不抽象」）→ 政策型，红线。
- 教的是小众领域的真知识（某框架的坑、某协议的细节），模型知识截止后才出现 → 知识型成分，留或修剪。

### 问 2 · harness 已自带？（环境型）

**证据标准**：指名道姓——哪个内建工具 / 功能覆盖了它，在当前会话确认可用。

典型对照：

| 过时 skill | 已被取代于 |
|---|---|
| 手搓 curl 网页搜索 / 抓取 | 内建 WebSearch / WebFetch 类工具 |
| 「帮我记住 X」写文件 hack | harness 自动记忆 |
| 手搓「先出计划等确认」流程 | 内建计划模式 |
| 手搓子任务分发说明 | 内建子 agent 机制 |
| 手搓定时 / 提醒 | 内建 schedule / cron 功能 |
| 通用代码评审流程 | 内建评审命令（如有） |

**反例**：skill 是对内建功能的**本地约定**（「本仓库跑测试用这条命令」「截图存这个目录」）→ 知识型成分，留。

### 问 3 · MCP 已接管？（环境型）

**证据标准**：指出接管它的 MCP server 与具体工具名，且该 server 已接入当前环境（不是「理论上有这么个 MCP」）。

典型：curl 拼 Slack / GitHub / Jira 请求的胶水 skill vs 对应 MCP；手写浏览器操作 cookbook vs playwright 类 MCP。

**反例**：MCP 只覆盖了一半（能发消息但不能建频道），skill 里另一半还有用 → 🔧 修剪到只剩没被覆盖的那半。

### 问 4 · 被吞并 / 重复？

**证据标准**：并排贴出两个 skill 的描述与正文骨架，指出重叠面；或给出触发词冲突的实例（一个任务两个 skill 都可能接）。

处理：留覆盖面大、维护新的那个；被并者独有的内容迁过去，空壳归档（🔗 合并）。

### 问 5 · 已腐烂？

**证据标准**：实际验证，不猜——

- 正文里的路径 / 主机 / URL：还存在吗（`ls`、配置文件里还有吗）？
- 引用的模型名 / API 版本：还在服役吗？
- 携带的脚本：`bash -n` / `python3 -m py_compile` 还过吗？跑一下最小用例还通吗？

腐烂 skill 的危害排序高于无用 skill：它会在触发后给出错误指引。修得动就 🔧 修，修不动就 ✂️ 归档。

## 三、盲测协议（能力型死刑复核）

1. **选题**：取该 skill 描述里最典型的触发任务，出一道具体的题（真实文件、真实输入，别用玩具题）。
2. **裸做**：开一个不加载该 skill 的子 agent 做这道题。提示词只给任务本身，不复述 skill 的方法论（复述了就不是盲测）。
3. **评分**：拿 skill 正文承诺的产出标准当评分表，逐条对照裸做结果。
4. **判**：
   - 裸做不逊色 → 问 1 坐实，✂️（证据：盲测记录一句话入报告）。
   - 裸做明显差，且差距正是 skill 教的内容 → ✅ 保留，记下差距。
   - 说不清 → ⏳ 缓刑，下次审计带着更好的题再来。

**成本控制**：一个 skill 只测一次、一道题；单次几分钟。skill 数量大时，只对「描述税前十」和「你犹豫的」盲测，其余按明显证据判。

**何时跳过盲测**：问 2 / 3 / 5 已坐实（有更硬的证据），或用户直接说删。

## 四、修剪手术指南（🔧）

混合型 skill 的正确刀法：

1. 逐行标注：这行是「方法」还是「事实」？
2. 方法行全删——模型已经会了。
3. 事实行保留并压缩成条目：路径、命令、账号名、约定、阈值。
4. 描述（frontmatter）同步重写：只描述剩下的事实，触发词收窄，把描述税降下来。
5. 结果常见 200 行剪成 10 行，描述税砍一半以上。

## 五、红线（绝不移除）速查

- 私有事实：账号、主机、内部流程、凭据使用方式。
- 政策约定：编码人的要求，不是模型的能力。
- 被别处引用的脚本 / 模板。
- 用户点名保留的。
- 证据不足的 → ⏳，不硬判。

## 六、边界案例三则

**案例 A · `code-review-checklist`（通用评审清单，描述税 190）**
盲测：拿一个真实 PR 让裸 agent 评审，清单上 12 项裸做覆盖 12 项，还多抓了一个清单外的并发 bug。问 1 坐实 → ✂️。

**案例 B · `deploy-checklist`（看似能力型）**
逐行标注发现一半是通用说教（「部署前跑测试」），另一半是本团队事实（「先发 canary 到 host-7，观察 15 分钟」「周五不发版」）。→ 🔧 修剪：说教删净，事实压成 8 行。

**案例 C · `web-research`（手搓搜索，描述税 240）**
问 2 坐实（内建搜索工具已覆盖）。但搜身发现正文里埋着内部 wiki 的 URL 和查询口诀——先把这两行迁进团队知识 skill，再归档。**过时 skill 里常埋着不过时的事实，搜身是归档前的必经步骤。**
